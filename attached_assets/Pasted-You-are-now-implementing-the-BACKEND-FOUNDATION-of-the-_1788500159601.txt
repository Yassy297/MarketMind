3. WATCHLIST DATA MODEL
============================================================

Design the model based on the existing Watchlist.ts and current architecture.

Do NOT unnecessarily create a complicated relational structure.

The data model must support:

Watchlist:

- _id
- userId
- name
- description (optional)
- sortOrder
- createdAt
- updatedAt

Watchlist membership/item:

- watchlistId
- canonical instrument identity
- symbol/display symbol
- company name
- market

- provider instrument identifier where available

IMPORTANT:

Do not use only the raw symbol as the global identity.

The same symbol can exist in different markets.

For example:

TSLA
TSLA on one exchange
TSLA on another exchange

must not accidentally be treated as the same instrument if the normalized instrument identity distinguishes them.

Reuse the existing MarketMind normalized instrument identity conventions.

Inspect marketData.types.ts and instrumentSearch.service.ts before deciding the exact fields.

Do not duplicate provider-specific response objects into Watchlist.

Watchlist stores canonical identity/metadata required to resolve the instrument later.

============================================================

Watchlist persistence must be provider-agnostic.

BAD:

Watchlist directly depends on Upstox API.

BAD:

Watchlist directly depends on Finnhub API.

BAD:

Watchlist stores raw provider response.

GOOD:

When live data is needed later:

Watchlist
    ↓
Stock/Market Data Service
    ↓
Provider Resolver
    ↓
Upstox / Finnhub / future provider
    ↓
Normalized MarketMind data

This keeps the Watchlist independent from provider changes.

============================================================
5. OWNERSHIP / SECURITY
============================================================

Every watchlist belongs to exactly one authenticated user.

Every API endpoint must use the existing authentication middleware.

NEVER accept userId from the frontend as an authoritative ownership value.

Always use the authenticated user's ID.

Example:

req.user.id

or whatever the existing middleware exposes.

Every query must be scoped by userId.

A user must NEVER be able to:

- read another user's watchlist
- modify another user's watchlist
- delete another user's watchlist
- add items to another user's watchlist
- remove items from another user's watchlist

Avoid IDOR vulnerabilities.

============================================================
8. DUPLICATE PREVENTION
============================================================

A watchlist must not contain the same canonical instrument twice.

Duplicate detection must be based on canonical instrument identity.

NOT:

symbol only.

Example:

HDFCBANK + IN
must be distinguishable from:

HDFCBANK + another market

Use the existing normalized market/instrument identity conventions.

Prefer a MongoDB unique compound index where practical.

Also perform application-level validation so the API returns a clean conflict response rather than a raw MongoDB duplicate-key error.

9. WATCHLIST NAME RULES
============================================================

Validate:

- name required
- trim whitespace
- reasonable maximum length
- reject empty names
- prevent accidental whitespace-only names

Decide whether duplicate watchlist names should be allowed.

Preferred:

Allow duplicate names only if the architecture makes that useful.

If preventing duplicates, enforce it safely at the database level with a compound userId + normalizedName field/index.

Do NOT make names globally unique.

Long Term
