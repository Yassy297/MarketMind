PART 1 — DELETE INDIVIDUAL RECENTLY VIEWED STOCK
==================================================

Currently MarketMind has a Recently Viewed section on:

1. Dashboard
2. Stocks / Stock Intelligence screen

The existing Recently Viewed backend is user-scoped and uses:
- server/src/models/RecentlyViewed.ts
- existing GET /api/stocks/recently-viewed
- existing backend recently-viewed recording logic

Add the ability to delete one specific recently viewed stock.

### Backend

Inspect the existing RecentlyViewed controller/service/routes and add the smallest appropriate authenticated delete operation.

Preferred API shape:

DELETE /api/stocks/recently-viewed/:symbol

However, before implementing, inspect existing route conventions and choose the route structure that best fits the current architecture.

Requirements:

- Must require existing authentication middleware.
- Must delete ONLY the authenticated user's matching recently viewed record.
- Never accept userId from the client.
- Do not delete the stock from:
  - Watchlists
  - Stock search
  - Stock data
  - Journal
  - Any global instrument data
- Deleting recently viewed history must have no effect on the stock itself.
- Handle symbols containing characters such as `.`, e.g. HDFCBANK.NS, safely.
- Return a clean success response.
- Return 404 if that stock is not present in the authenticated user's recently viewed history.
- Do not expose database errors or stack traces.

UI requirements:

- Do NOT install another icon package.
- The trash icon should be red using the existing semantic negative/destructive color token/theme.
- Do not introduce a new hardcoded red color if an existing semantic negative/destructive class/token exists.
- Keep the existing card layout and visual hierarchy.
- The trash icon should be visually subtle but clearly actionable.
- Place it consistently on the right side of the recently viewed card, without disturbing the stock name/company/date layout.

- Provide an accessible aria-label/title such as:
  "Remove TSLA from recently viewed"

Clicking the trash icon must NOT navigate to the stock page.

Stop event propagation where necessary so:
- Clicking the stock card → opens stock

Use the existing React Query setup.

- Restore/retain the stock in the UI.
- Show the project's existing friendly error/toast mechanism.
- Do not expose backend stack traces.

Do NOT add a confirmation modal for deleting a single recently viewed item unless the existing UX conventions clearly require it. This is a low-risk history cleanup action and should preferably be one click.

PART 2 — JOURNAL CRUD → RECENT ACTIVITY
==================================================

The existing Journal supports:
- Add/Create trade
- Edit/Update trade
- Delete trade

The existing Dashboard has a Recent Activity section backed by the existing Activity infrastructure and GET /api/dashboard.

Add Journal activity events to that existing system.

DO NOT create a new activity collection or a second activity mechanism.

First inspect:
- existing Activity model
- activity service/helper
- existing activity event types
- dashboard service/controller
- existing watchlist activity implementation

Reuse the same architecture and conventions.

### Required Journal activity events

When a user:

1. Creates/adds a trade
2. Updates/edits a trade
3. Deletes a trade

create a Recent Activity event.

Use clear human-readable activity messages.

Examples:

CREATE:
"Trade added"
"Added TSLA trade to Journal"

UPDATE:
"Trade updated"
"Updated TSLA trade in Journal"

DELETE:
"Trade deleted"
"Deleted TSLA trade from Journal"

Use the actual instrument symbol/name available on the trade.

If the existing Activity system has a specific event/type/category structure, follow it rather than inventing a new format.

The activity should contain enough information for the existing Dashboard Recent Activity UI to render naturally.

### Activity timing

Activity timestamps must reflect the actual CRUD operation time.

Most recent events should appear first according to the existing Recent Activity ordering.

### User isolation

Activities must belong to the authenticated user.

A user must never see another user's journal activity.

Use req.user.id / existing authenticated user context.

Do not accept userId from the frontend.

### CRUD behavior

CREATE:
- If the trade is successfully created, record activity.
- If trade creation fails, do not create activity.

UPDATE:
- If the trade is successfully updated, record activity.
- If update fails, do not create activity.
- Use the updated trade/instrument information where appropriate.

DELETE:
- If deletion succeeds, record activity.
- Since the trade will no longer exist after deletion, capture the necessary symbol/name before deleting so the activity can still say which trade was deleted.

Activity logging should NOT cause a successful Journal CRUD operation to fail.

Follow the same failure-handling pattern already used by Watchlist activity logging:
- primary business operation succeeds
- activity logging is attempted
- activity logging failure is logged server-side
- the original CRUD request remains successful

Do not duplicate activity events.
